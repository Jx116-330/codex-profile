# Embedded Domain — 嵌入式固件纪律

TC387 多核固件 + 外设驱动 + 编译/链接排错的领域细则。本文件在嵌入式固件任务时读取。

## 搜索

- 写新代码前，先用 Grep/Glob 找现有实现与邻近模块，复用已有模式
- 查参数/配置值：进源码取实际值（宏定义、初始化代码），不背记忆数字
- 引脚占用查证：调用点 → 宏定义 → 物理引脚全链路（`libraries` 里的宏可能重定义引脚）
- 外部文档（WebSearch/WebFetch）仅在本地源码检查不足时使用
- 不熟悉的模块：先向上看地图（模块结构/调用者/数据流）再钻细节

## 编码

- **最小改动**：永远选最简单、最直接的方案；拒绝冗余设计、过度工程、多余抽象
- 一次只解一个 blocker，解完再验证
- 避免无关重构、无关重命名、投机清理
- 新代码匹配邻近代码的注释密度、命名、惯用法
- 编译/链接失败：修最小处，先验证构建产物与链接输出，不猜

## 调试

- 第一轮怀疑硬件（引脚改没改、线束、接触、板子改动），再钻软件
- **先建立反馈回路**：优先使用快速、确定性、可自动化的 pass/fail 信号（遥测流/台架阶跃/复现脚本）；暂时没有信号时继续有界的静态分析或最小复现，并标明结论置信度
- 纪律循环：复现 → 最小化 → 假设 → 仪器化 → 修复 → 回归
- **假设要可证伪且排名**：3-5 个假设，每个陈述"若 X 是原因，改 Y 会让 bug 消失"；先展示排名，随后继续低风险测试；只有范围、安全边界或已批准参数会改变时才等待用户决定
- 一次只改变量；调试日志带唯一前缀（`[DEBUG-xxxx]`），清理时一次 grep 全删
- 信号验证优先于高层算法改动；先验证信号存在，再动算法
- 先自行排错复现，再拉用户一起看现象
- 运行时行为无变化时：验证最终构建产物（flash 后 behavior 不变 → 查 build 产物/链接输出）
- **修完必复盘**：由 agent 内部回答"什么能阻止这个 bug？"并在交付中简述；只有需要用户作架构或产品决策时才提问。若是架构问题（无测试缝隙/耦合），交架构审查

## 重构

- 关键数据流（DR 类、跨核通信）改前：先画数据流全图（生产者/消费者/共享区/同步点）
- 替代算法：并行影子实现 + 消费端开关，不直接改写现有链路
- 数据口径检查：指令 vs 地速、不同传感器坐标系、符号极性

## 完成标准

- 纯软件逻辑改动：编译 + 自审 = 完成
- 硬件/参数/链路改动：实机验证才算完成；实机条件不满足时报"代码侧就绪 + 实机待验证 + 明确缺口"
- 交活前自审五检查点：范围有界 / 无无关变更 / 验证具体 / 风险明确 / 诚实标注

## 协作

- 复杂任务且子代理能大量省时（如跨模块并行搜索/审查）→ 用 Agent 工具
- 简单任务保持单线程，不启动子代理
